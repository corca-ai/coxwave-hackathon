# DSPy + OpenAI Evals 도입 계획

## Problem 1-Pager

### Background
- 현재 데모는 `main.py` 중심의 오케스트레이션이며, 실제 LLM 연결은 Clarifier만 구현되어 있다.
- 에이전트 프롬프트가 의도대로 작동하는지 정량적으로 검증할 수 있는 평가 루프가 없다.
- DSPy 및 OpenAI Evals를 활용한 체계적 평가/개선 체계를 구축하려는 요구가 있다.

### Problem
- 프롬프트 품질을 측정/비교할 기준 데이터셋·지표·루프가 없어 개선이 수동/주관적이다.
- 에이전트별 단위 테스트와 데모 E2E 테스트는 있으나, 품질 메트릭 기반의 자동 최적화(프롬프트/모듈 개선) 체계가 없다.
- 운영(어드민) 관점에서 “평가 → 개선 → 재평가”를 반복하는 경로가 정의되어 있지 않다.

### Goal
- 에이전트별 평가 데이터셋/메트릭 정의 및 실행 경로를 마련한다.
- DSPy를 통해 최소 1개 에이전트의 프롬프트/모듈을 자동 최적화하는 루프를 구축한다.
- OpenAI Evals 기반의 외부/표준화 평가 실행 계획을 마련하고, 로컬/클라우드 평가를 연결한다.
- 관측 가능성(입출력 payload 출력)과 재현성(로그/아티팩트)을 확보한다.

### Non-goals
- 완전한 지식 그래프/수집 파이프라인 구현
- 모든 에이전트를 즉시 DSPy로 전환
- 대규모 데이터셋 구축 및 장기 모델 튜닝
- 프로덕션 UI/대시보드 구축

### Constraints
- 데모/테스트는 기본적으로 입력·출력 payload를 항상 출력한다.
- 에이전트 간 연결은 입력 payload를 통해 “실제로 전달됨”이 확인되어야 한다.
- 테스트 suite는 “데모 E2E + 각 에이전트 단위 테스트” 구조를 유지한다.
- 모든 반복 루프는 상한을 가지며, 기본값은 env로 설정하고 CLI 옵션으로 오버라이드 가능해야 한다.
- 실행/테스트는 `.env`를 기본 로드한다.
- `*_req_req.md` 등 프롬프트 로그 파일은 항상 유지한다.

## Repo Snapshot (Relevant)

- `agents_impl.py`: Clarifier 실제 구현 + 나머지 Mock 연결

## 계획 (Phased Plan)

### Phase 0: 평가 대상/메트릭 정의
1. **평가 대상 선정 (MVP)**
   - 우선 Clarifier + Planner + Extractor 중 1~2개를 선정 (최소 1개 DSPy 최적화 대상).
2. **데이터셋 스키마 정의**
   - 에이전트별 입력/기대 출력(JSON) 형식을 명문화한다.
   - 예: Clarifier는 `is_clear_enough`, `clarifying_questions` 유무, 질문 수, 모호성 처리 등.
3. **메트릭 설계**
   - 규칙 기반 + LLM 기반 판정을 혼합.
   - 성공/실패 기준과 점수화 규칙을 문서화한다.

### Phase 1: 로컬 평가 하네스 구축 (Admin CLI)
1. **평가 실행 CLI 추가**
   - 예: `python3 evals_cli.py --agent clarifier --dataset datasets/clarifier.jsonl`
   - `.env` 자동 로드, 입력/출력 payload 항상 출력.
2. **아티팩트 저장**
   - `tests/_artifacts/` 또는 `evals/_artifacts/`에 run 로그/요약 저장.
3. **단독 실행 경로**
   - 각 에이전트별 “단독 평가” 경로를 제공한다.
4. **루프 상한**
   - 평가 반복/샘플링 루프에 상한을 두고 env/CLI로 오버라이드 가능하게 한다.

### Phase 2: DSPy 적용 (최소 1개 에이전트)
1. **DSPy 모듈/시그니처 설계**
   - `docs/implementation.md` 예시를 기준으로 최소 1개 에이전트에 DSPy Signature/Module을 정의.
2. **컴파일/최적화 루프**
   - DSPy Optimizer(MIPRO 계열 등)를 사용해 metric 기반 컴파일.
   - 반복 횟수 상한을 env/CLI로 제어.
3. **베이스라인 대비 개선 확인**
   - 동일 데이터셋으로 baseline vs optimized 비교 리포트 생성.
4. **출력 호환성**
   - `main.py`의 dataclass 출력 스키마와 완전히 호환되도록 보장.

### Phase 3: OpenAI Evals 연계 계획
1. **데이터셋 매핑**
   - 로컬 JSONL → OpenAI Evals/데이터셋 포맷으로 매핑 가능한 스키마를 확보.
2. **평가 파이프라인 구분**
   - 에이전트 단위 평가(단일 단계) vs 데모 E2E 평가(전체 시나리오) 구분.
3. **결과 추적**
   - Eval run ID/요약 리포트/비교 결과를 로컬 아티팩트로 저장.

### Phase 4: “개선 루프” 운영 절차 정리
1. **운영(어드민) 루프 정의**
   - 데이터셋 추가 → 평가 → DSPy 최적화 → 재평가 → 결과 저장.
2. **실패 분석 루틴**
   - 실패 케이스 샘플과 원인 요약을 자동 기록.
3. **회귀 방지**
   - 최소 기준(품질 임계치) 미만이면 자동으로 “rollback/보류” 처리.

- 에이전트별 평가 데이터셋 스키마 문서
- 로컬 평가 실행 CLI + 로그/아티팩트 저장 경로
- DSPy 적용 예시(최소 1개 에이전트)와 개선 전/후 비교 리포트
- OpenAI Evals 연계 계획 문서 및 실행 경로 요약

## 성공 기준 (Definition of Done)
- 최소 1개 에이전트가 DSPy 최적화 루프를 거쳐 baseline 대비 지표 개선이 확인된다.
- 에이전트 단위 평가 + 데모 E2E 평가가 동일 실행 패턴으로 재현 가능하다.
- 모든 평가/최적화 루프가 상한을 가지며 env/CLI에서 제어 가능하다.
- 입출력 payload와 평가 로그가 기본 출력 및 아티팩트로 보존된다.
